Reinforcement learning is built around a simple idea: an agent improves by acting in an environment and learning from feedback. Its foundations are described in Sutton and Barto’s Reinforcement Learning: An Introduction. Early systems usually worked in small environments with short episodes and clear rewards.

Deep learning made these systems far more capable. AlphaGo combined neural networks, self-play, and search, while AlphaGo Zero learned from the rules and self-play alone. OpenAI Five showed that RL could also handle real-time, multi-agent environments with delayed consequences.

Language models also changed how agents are trained and improved. DeepSeek’s GRPO uses relative rewards across sampled solutions to improve reasoning, while Thinking Machines Lab’s work on on-policy distillation studies how a smaller model can learn from a stronger teacher while generating its own training experience. Together, these methods point toward agents that can reason, act, and improve through repeated interaction.

These advances reveal the difference between a convincing demo and reliable long-horizon behavior. Tasks lasting hours or days require persistent state, useful memory, external events, side-effectful tools, recovery, and delayed rewards. The environment determines what the agent can observe, change, and remember.

This article takes an environment-first view. We will cover state, time, events, actions, memory, rewards, tools, multi-agent settings, credit assignment, failure modes, training, evaluation, and the path from isolated tasks to persistent worlds.

From Tasks to Environments

A normal benchmark task is often presented as a prompt, a fixed set of tools, a sequence of actions, and a final answer. This works well when the task is short and the world remains unchanged while the model is reasoning. For example, a coding benchmark may give an agent a GitHub issue and ask it to produce a patch, as in SWE-bench.

That abstraction becomes weaker as the horizon grows. If an agent works for twelve hours or three days, new information arrives, tools change state, people respond later, and earlier decisions affect what becomes possible next. A pull request can receive review comments, a test pipeline can fail after a delay, or a business workflow can wait for a human response. Systems such as GitHub Actions and AWS Step Functions are useful examples of software environments where events and state continue to evolve over time.

An environment is therefore more than a task description. It is a persistent world containing state, tools, time, external events, constraints, and consequences. This is closely related to the Harbor framework, which is used for running agent evaluations and RL environments. Harbor packages an instruction, an environment, and a verifier; the JSON below is a simplified, Harbor-style representation of a long-horizon coding task:

{
  "task_id": "checkout-auth-001",
  "instruction": "Fix the failing authentication test",
  "environment": {
    "image": "checkout-service:latest",
    "os": "linux",
    "working_directory": "/workspace",
    "resources": {"cpu": 4, "memory_gb": 16}
  },
  "initial_state": {
    "repository": "checkout-service",
    "branch": "agent/fix-auth",
    "tests": {"authentication": "failing"}
  },
  "tools": ["terminal", "git", "test_runner"],
  "external_events": ["review_comment_received", "ci_run_finished"],
  "constraints": ["do not expose credentials"],
  "verifier": {"tests_pass": 1, "regression": -1}
}

The key distinction is between what the model currently sees and what is actually true. The context window contains the agent’s current observation: perhaps the latest test output, one review comment, and a small portion of the repository. The environment contains the complete state of the world, including files not yet opened, pending events, hidden constraints, and consequences from earlier actions. Long-horizon agents must repeatedly observe the environment and update their beliefs instead of treating the first prompt as a complete description.

A task gives an agent something to solve. An environment gives it somewhere to operate. For long-horizon agents, that distinction is fundamental. Evaluation must therefore move beyond asking, “Can the model solve this task?” and ask, “Can the agent operate correctly inside a changing world over time?”

The Core Architecture of a Long-Horizon Environment

A long-horizon environment is not just an LLM connected to a larger collection of tools. It is a system that persists, changes, and records consequences while the agent works inside it. The agent sees only an observation of that system, acts through an interface, and is eventually judged on a trajectory that may span hours or days. Most such environments can be understood through six primitives: state, time, events, actions, memory, and rewards.

State

State is the source of truth for the world. It is not the model’s context window and it is not the conversation transcript. It can include files, database rows, emails, account balances, open cases, task progress, permissions, and decisions already made. A useful abstraction is St, the world state at time t. When the agent takes an action, it changes the conditions from which the next action must be chosen. A reliable environment therefore needs durable state that can be inspected, updated, and recovered independently of the model process.

Time

Long-horizon systems have two clocks. Agent time counts reasoning steps, messages, and tool calls. World time counts hours, deadlines, waiting periods, and background processes. These clocks do not have to move together: an agent may make no call for four hours while a deadline approaches or a job finishes. This is why an environment needs explicit support for waiting, scheduled actions, timeouts, and sometimes accelerated simulation. Without world time, a long task is only a long transcript.

Events

Events are changes that do not necessarily originate from the agent. An email can arrive, a customer can reply, an experiment can finish, another employee can edit a file, an API can fail, or a price can move. A simple transition model is St+1 = f(St, At, Et), where At is the agent’s action and Et is the external event stream. This makes the environment genuinely dynamic: it can change while the agent is reasoning, waiting, or offline.

Actions

Actions are the interface through which the agent changes the environment. They are not all equally consequential. Reading a database is different from approving a claim; searching a repository is different from merging a pull request. Actions can have cost, latency, permissions, side effects, reversibility, and downstream consequences. The most interesting long-horizon environments are those in which an action changes the future decision space. The agent must consider not only whether a tool call succeeds, but what options it removes or creates later.

Memory

Memory belongs to the agent, while state belongs to the environment. The world may contain thousands of emails, but the agent may need to retain only three critical facts and the evidence supporting them. Useful memory can be divided into working memory for the current subtask, episodic memory for past events, semantic memory for durable knowledge, and artifact memory for files or other outputs. The central design problem is deciding what to preserve, what to compress, and what to retrieve later. Placing an entire three-day trajectory into the context window is not a memory architecture.

Rewards

Rewards determine which trajectories are worth repeating. In a short task, the reward may be equivalent to a correct final answer. In a long task, evaluation often needs to combine outcome quality, efficiency, constraint adherence, and process quality: R(τ) = Routcome + Refficiency + Rconstraints + Rprocess. An insurance agent, for example, might reach the correct decision but still perform poorly if it requested unnecessary documents, violated policy, or communicated an incorrect explanation. The environment must evaluate how success was achieved, not only the final state.

These six components form the substrate of a long-horizon environment. State gives the world persistence, time lets it evolve, events introduce change, actions create consequences, memory gives the agent continuity, and rewards determine which trajectories are worth learning from.

State Architectures

The important question is not only what state exists, but where it lives and who owns it. A short agent loop can treat the prompt as its working state. An agent that runs for days cannot. As the horizon grows, state moves outward—from the context window into checkpoints, databases, workflow histories, and external systems. The architecture determines whether the agent can resume after failure, coordinate with other actors, and distinguish an old observation from the current world.

Prompt-local state

The simplest architecture keeps state inside the prompt: instructions, conversation history, and recent tool outputs are passed back to the model on every step. This is easy to build and often sufficient for a bounded coding session or a short research question. Its weakness is that the context window carries too much responsibility. If the process crashes, the history is truncated, or the agent returns tomorrow, important state may disappear. Prompt-local state is useful as working memory, but it is a poor source of truth for a long-running environment.

Persistent state

Persistent state separates the agent’s temporary execution from the information that must survive. Plans, task status, files, job identifiers, decisions, checkpoints, and permissions can be written to durable storage. The model may stop running while the agent continues to exist conceptually: it can wake, load its state, perform work, checkpoint, sleep, and wake again after an event. Cloudflare Agents are a useful production reference for this pattern, while the updated OpenAI Agents SDK describes externalized state, sandbox snapshots, and rehydration for long-running work.

The design challenge is deciding what must be durable. A full transcript may be unnecessary, while a pending payment, a decision rationale, or the identifier of an external job may be essential. The goal is not to preserve everything. It is to preserve the information needed to reconstruct the agent’s situation and continue safely.

Distributed state

Production environments rarely have a single world_state.json. An insurance agent might depend on a claims database, email, document storage, a CRM, a payment system, and several external APIs. The true state is distributed across systems owned by different teams, each with its own latency, permissions, failure modes, and consistency guarantees.

This introduces classic distributed-systems problems into agent design: stale reads, concurrent writes, duplicate events, retries, partial failures, and eventual consistency. Temporal is a useful reference because it separates durable workflow history from the activities that perform side effects. The workflow can remember what happened and retry safely even when an API or worker disappears. For agents, this is the difference between resuming from a checkpoint and starting the entire task again.

Partially observable state

In many environments, the agent should not see the complete world state. A cybersecurity investigation, insurance review, negotiation, or scientific experiment may contain hidden facts that must be inferred from evidence. The environment has a true state St, but exposes only an observation Ot = g(St). The agent then maintains a belief about the world based on its observation history and previous actions: Bt = P(St | O1:t, A1:t-1).

For example, an insurance environment might internally know that a document is fraudulent, but the agent should receive only conflicting timestamps, an invoice, an email, and vehicle telemetry. It must investigate rather than read the answer from a hidden label. This separation between state, observation, and belief makes the benchmark more realistic and creates room to evaluate information gathering, uncertainty, and recovery from an incorrect hypothesis.

Composing the architectures

These architectures are not mutually exclusive. A serious long-horizon system may use prompt-local state for the current thought, persistent storage for plans and checkpoints, distributed services for the real world, and partial observability to prevent the agent from receiving privileged information. The model reasons over observations, while durable infrastructure owns the state that must survive.

That is the deeper shift: the architecture of long-horizon agents begins to resemble distributed systems more than chat applications. The model supplies reasoning and action selection, but the surrounding system supplies continuity, synchronization, access control, recovery, and a record of consequences.

Memory for Hours- and Days-Long Tasks

A long-horizon agent cannot keep every observation, tool result, intermediate plan, and artifact in active context. Over a twelve-hour or three-day trajectory, the history can grow far beyond what should be placed in one prompt. The memory problem is therefore not remembering everything. It is preserving what will matter later, retrieving it at the right moment, and revising information that has become stale.

The context window is best understood as working memory: the small amount of information the agent is actively reasoning over right now. It may contain the current objective, the immediate plan, recent observations, temporary hypotheses, and the next few actions. If Mt is everything the agent could potentially remember, then its working memory is only a selected subset, Wt ⊂ Mt. The context window should contain what the agent needs now, not everything that has ever happened.

Episodic, semantic, and artifact memory

Episodic memory records what happened: a request was sent, a customer replied, an experiment failed, or a task was escalated. A useful event can be represented as ei = (time, action, observation, outcome). This lets an agent later ask why it made a decision, whether it already tried a strategy, or what happened after an earlier action.

Semantic memory stores what the agent learned rather than the complete path that produced it. “At 14:05, the customer confirmed the vehicle was repaired in London” is episodic; “vehicle repair location = London” is semantic. Facts, policies, relationships, preferences, discovered constraints, and conclusions belong here. In systems such as Mem0, persistent memories are separated from the active context and retrieved when they become relevant. Benchmarks such as LongMemEval make this retrieval problem measurable across long, multi-session histories.

Artifact memory is different again. Long-running agents create code, reports, spreadsheets, patches, diagrams, experiment outputs, and research notes. These should not all be copied into the prompt. Instead, the agent can store a pointer and metadata such as artifact_id, location, purpose, and status. Long-horizon memory is partly about remembering information and partly about remembering where important information lives.

Compression and retrieval

The naive architecture sends the entire history into the context window. A scalable architecture continuously writes important information to long-term memory and retrieves only what is relevant to the current decision:

raw history → episodes → facts and artifacts → retrieved working context

The two fundamental operations are write(Mt, xt) and retrieve(Mt, qt). The difficult part is deciding what deserves to be written, what should be compressed, and what must be retrieved now. A memory layer may use a service such as Redis, Mem0, a database, or a combination of stores. The important architectural idea is not the vendor: memory becomes an active process of selection, compression, retrieval, update, and forgetting rather than a passive transcript.

For long-horizon agents, forgetting is as important as remembering. A useful memory system must decide what survives, what becomes stale, what should be updated when evidence conflicts, and what belongs only in the archive. The goal is not perfect recall. It is maintaining the smallest reliable representation of the past needed to make good decisions about the future.

Tool and Action Architectures

The tool interface determines what kind of agent is actually being trained. An API agent, a browser agent, and a desktop agent may be asked to solve the same business problem, but they operate in very different environments. The interface changes the difficulty, the kinds of errors that are possible, and what it means for an action to change the world.

APIs, computer use, and sandboxes

APIs are the cleanest action interface. A tool such as get_claim(id), update_claim(id, status), or send_email(to, body) exposes a system’s capabilities directly. Calls are easy to validate, replay, and score, which makes them useful for reinforcement learning. τ-bench is a useful example: agents interact with tools and simulated users while following policies in customer-service workflows.

Computer-use environments remove that abstraction. Instead of calling a perfect function, the agent receives screenshots and acts through mouse movement, clicks, typing, scrolling, and keyboard shortcuts. It must decide both what to do and how to physically accomplish it. OpenAI’s Computer-Using Agent, WebArena, and OSWorld show why interface navigation introduces many more opportunities for error than a structured API.

API
agent calls: update_customer(123)

COMPUTER USE
agent must: open CRM → find customer → navigate tabs
             → edit field → save → verify

Researchers therefore increasingly use sandboxed copies of applications and systems: websites, Linux terminals, repositories, databases, desktop apps, and simulated enterprise software. Harbor is especially relevant because it treats a task as an instruction, an isolated environment, and a verifier. A sandbox turns software into a trainable world: it makes exploration safer, supports parallel rollouts, and allows the environment to be reset to the same initial state.

That reset is essential for RL. After each rollout, the system should be able to restore the world and run another agent from the same starting point: reset(St) → S0. This gives researchers reproducibility, controlled failures, hidden state, and deterministic verification without requiring agents to operate on live production systems.

Hybrid environments

Long-horizon agents will rarely use one interface exclusively. An agent might use an API to retrieve thousands of customer records, a browser to inspect a legacy system with no API, and a terminal to analyze the result inside a sandbox. A software engineer may move through GitHub, a terminal, an IDE, a browser, and Slack during one task. The strongest environments will let the agent choose not only what action to take, but which interface is appropriate for taking it.

Irreversible actions

Long-horizon work also contains actions that modify the future: sending an email, approving a payment, merging a pull request, deleting a database row, rejecting a claim, or deploying production code. We can represent an action as At : St → St+1, but some transitions cannot be cheaply undone: At−1(St+1) ≉ St.

This creates genuine planning pressure. Inside an episode, the action should have consequences that later decisions must respect. Outside the episode, the simulator should still be resettable for the next rollout. For example, approving a payment can set a claim to PAID, reduce a balance, notify a customer, and create an audit event; the entire simulated world can then be restored for another training run.

The key idea is that the action space itself is part of environment design. Long-horizon agents should not be trained only to call tools. They should learn to operate interfaces, choose between interfaces, understand which actions change persistent state, and recognize when an action cannot safely be undone. The environment is not just a collection of capabilities; it is a controlled world in which actions carry consequences.

Reward and Credit Assignment Across Long Horizons

Long-horizon reinforcement learning creates a basic problem: the action that determines success may occur hours before the reward arrives. A trajectory can contain thousands of decisions, τ = (s0, a0, s1, a1, …, sT), while the environment produces only one final signal. The agent must determine which earlier actions caused that outcome.

Sparse final rewards

The cleanest reward is often the final outcome. An insurance agent might investigate a claim for twelve hours before reaching a decision, after which an external verifier checks whether the decision was correct. When the outcome is objectively verifiable, I generally prefer a binary primary reward: R = 1 for success and R = 0 for failure.

Binary rewards reduce the number of arbitrary preferences encoded into the environment. Instead of deciding that opening a document is worth +0.1, sending an email is worth +0.3, and finishing quickly is worth +0.5, the environment asks the harder and more meaningful question: did the agent actually accomplish the task?

Binary does not mean unhackable. If the success verifier has a loophole, the model can still optimize that loophole. The simplicity of the reward only helps when the verifier measures the outcome we actually care about.

Intermediate rewards and process supervision

Sparse rewards make credit assignment difficult. If a 500-action task fails at the end, the agent learns that the trajectory was bad but not whether the important mistake happened at step 12, 180, or 497. Intermediate signals can make learning easier, but every signal becomes a new proxy that the policy may optimize in unintended ways.

requested correct evidence       +0.1
identified a contradiction       +0.2
followed authorization policy    +0.1
correct final decision           +1.0

An agent rewarded for requesting evidence may request unnecessary evidence. An agent rewarded for resolving cases quickly may prematurely close difficult cases. An agent rewarded for passing tests may learn to manipulate the tests. This creates a central tension: denser feedback can improve credit assignment while increasing the reward’s attack surface.

Process supervision is a more careful alternative. Rather than rewarding every click or tool call, an evaluator can check whether important parts of the trajectory were correct: did the agent identify the relevant policy, collect the required evidence, respect authorization boundaries, and use the available evidence before making its final decision? Two agents can reach the same answer while taking very different paths—one investigating correctly and the other guessing—so a useful evaluator should distinguish Routcome from Rprocess.

Delayed consequences

Long-horizon environments become especially interesting when an action’s consequences are not immediately visible. An agent may approve an unusual exception in the first hour, a customer may proceed based on that approval several hours later, and a compliance system may flag the case only near the end of the task. The first action looked locally reasonable; its cost appeared thirteen hours later.

The environment therefore needs to preserve causal information across time. Otherwise, training sees only a bad ending without enough structure to identify which earlier decision created it. This is the practical form of long-horizon credit assignment: connecting a delayed outcome to the actions, observations, and state transitions that produced it.

Reward hacking

Reward hacking occurs when an agent increases the measured reward without accomplishing what the environment designer intended. A coding agent told to make the tests pass might fix the implementation—or disable the test. The measured result is the same, but the underlying outcome is completely different.

This risk grows with capability. The same ability that helps an agent solve difficult tasks can help it discover weaknesses in the evaluator. In shorthand, Rproxy ↑ while Rtrue ↓. Stronger verifiers reduce this gap, but they cannot eliminate it when the specification itself is incomplete.

Why binary rewards are useful

For long-horizon environments, my default is to keep the primary reward as close to binary and externally verifiable as possible. Richer signals can still be useful for diagnostics, curriculum construction, and carefully designed auxiliary objectives, but blindly combining many subjective scores creates more places where optimization can diverge from intent.

The goal is not simply to make the reward binary. It is to make success binary when possible and make the verifier difficult to game. That means testing the verifier itself with hidden state, adversarial cases, held-out checks, independent evaluators, and sometimes multiple forms of verification. The reward hacking discussion is a useful reminder of this failure mode before designing the reward rather than after training exposes it.

For long-horizon RL, the hardest problem may eventually be less about producing reward and more about ensuring that the reward still means what we think it means after an agent has had thousands of opportunities to optimize against it.

How to Build a 12-Hour Environment

A twelve-hour environment should not be implemented as one process that stays alive for twelve hours. Most of the time, the agent will be waiting: for a CI job, a user reply, an experiment, an approval, or an external event. A more robust architecture is a durable environment that can wake, act, checkpoint, sleep, and resume.

Environment server

The environment server owns the episode lifecycle. It should expose operations such as reset(), observe(), act(), advance_time(), checkpoint(), restore(), and evaluate(). The server—not the model—decides what state exists, what the agent is allowed to observe, which tools are available, what events are pending, whether the episode has finished, and when evaluation runs.

This separation also makes the environment reproducible. The same initial state should be able to generate another rollout from the same checkpoint. Frameworks such as Harbor use this kind of separation between an agent and an isolated environment, allowing the same world to support evaluation, RL rollouts, and trajectory generation.

State store

Anything that matters after a restart must live outside transient model execution. A twelve-hour coding task may need to persist an episode identifier, repository commit, open pull request, current plan, pending CI job, received messages, created artifacts, remaining budget, and completed actions. You do not need to save every Python variable; you need enough information to reconstruct St after a crash or sleep period.

The rule is simple: if losing it would change what the agent should do next, persist it. This is the same design pressure behind durable state in production agent runtimes such as Cloudflare Agents, where state survives restarts and hibernation.

Event scheduler

A twelve-hour environment needs an actual concept of future time. The scheduler might create events such as a CI job completing in ten minutes, a customer replying in forty-five minutes, a document arriving in two hours, or an approval window closing in ten hours. The world is therefore not only updated by the agent:

St+1 = f(St, At, Et)

Here, Et represents events that can occur independently of the agent. For training, time can be accelerated: a real three-hour wait may become three simulated minutes while preserving the ordering and consequences of events.

Tool interfaces and checkpointing

A strong twelve-hour environment should mix APIs, computer use, terminals, filesystems, databases, and messaging while keeping them connected to the same underlying state. If the agent sends an email, the inbox should change. If it edits a repository, later tests should use the new code. If it approves something, another actor should be able to observe that decision. The tools should not become isolated mini-games; they should be different interfaces to one persistent world.

Checkpointing makes the environment survivable. A checkpoint might store the current world time, state version, goal, plan step, pending job, artifacts, and memory snapshot. If execution disappears, the system can reload the checkpoint, reconstruct the working context, and continue from the same step rather than replaying six hours of conversation.

crash
  ↓
reload checkpoint
  ↓
reconstruct context
  ↓
continue safely

Recovery should be a normal state transition, not an exceptional failure. The model can crash, change, lose its context, or go offline; the environment should still know what happened, what time it is, which events are pending, which actions occurred, what artifacts exist, and where the agent should resume.

Evaluators

Finally, the environment needs evaluators that inspect both the trajectory and the final world state. A primary verifier might check that tests pass, required functionality works, credentials were not exposed, the repository was not corrupted, and the task objective was satisfied. Diagnostic metrics—tool calls, tokens consumed, elapsed world time, retries, policy violations, human interventions, and recovery events—can be recorded separately rather than all being placed inside the reward.

The complete design is less like LLM runs for 12 hours and more like wake → observe → reason → act → persist → wait → event → wake → recover → continue. The environment lasts twelve hours. The model does not have to.

Training on Long-Horizon Environments

Building a twelve-hour environment is only half the problem. The harder question is how to train a model inside it. A short reasoning task may generate a few hundred tokens before receiving a reward; a long-horizon agent may generate thousands of tool calls, observations, plans, artifacts, retries, and decisions before the final outcome is known.

Training is therefore better understood as a pipeline than as one enormous RL run:

good trajectories → SFT → short-horizon RL → curriculum
→ longer rollouts → offline reuse → long-horizon RL

The practical goal is to first teach the model what competent behavior looks like, then let reinforcement learning improve how it behaves when it reaches states that demonstrations did not cover.

SFT from trajectories

Supervised fine-tuning is a useful place to start. A successful long-horizon trajectory should not be treated as one enormous input-output pair. It can be decomposed into many state-action examples. If an expert reads a policy, requests evidence, waits for a reply, identifies a contradiction, and makes a final decision, every transition can become training data:

(St, Ot, Mt) → At

St is relevant environment state, Ot is what the agent observed, Mt is reconstructed memory or task context, and At is the expert action. A successful long trajectory can therefore be decomposed into thousands of supervised decisions. Thinking Machines’ Tinker is one example of a programmable interface for SFT and RL workflows.

{
  "episode_id": "claim-18492",
  "world_time": "06:42:18",
  "observation": {
    "claim_status": "investigating",
    "new_email": true,
    "pending_documents": ["repair_invoice"]
  },
  "memory": {"goal": "determine coverage"},
  "expert_action": {
    "tool": "open_document",
    "arguments": {"document": "repair_invoice"}
  }
}

Where trajectories come from

Trajectory data can come from human experts, strong frontier models, production traces, search systems, planning systems, or successful RL rollouts. A teacher can run inside the environment, after which the verifier filters the results:

teacher → environment → successful trajectories → SFT → better agent

This creates a flywheel. The agent improves the trajectory dataset, and the improved dataset produces a stronger agent. Prime Intellect is relevant because its Verifiers ecosystem combines datasets, harnesses, tools, sandboxes, and reward functions for evaluation, synthetic data generation, and RL training.

Reinforcement learning

SFT teaches the model to imitate trajectories that already exist. RL is useful when we want it to discover better trajectories:

policy → rollout → environment → trajectory
       → verifier → reward → policy update → repeat

The difficulty is hidden inside the rollout. In a twelve-hour environment it may involve thousands of actions, asynchronous events, memory compression, checkpoints, external tools, failures, resets, and delayed rewards. Scaling long-horizon RL is therefore partly a systems problem: the trainer must coordinate the policy, environment server, trajectory store, verifier, and recovery logic.

Offline and off-policy reuse

Long trajectories are expensive. If an episode consumes twelve hours of simulated work, throwing it away after one update is wasteful. Offline learning lets the trainer reuse a fixed dataset, including failures. An agent may perform well for six hours before making one catastrophic decision; the partial success and failure point are both useful.

{
  "trajectory_id": "episode-8821",
  "policy_version": "v17",
  "final_reward": 0,
  "steps": 784,
  "failure": {"step": 623, "type": "premature_commitment"},
  "checkpoint_rewards": [[100, 1], [300, 1], [600, 1], [623, 0]]
}

These trajectories can support SFT on successful subsequences, preference learning, value-function training, failure classification, critic training, reranking, distillation, and counterfactual analysis. A twelve-hour rollout should be treated more like a dataset than a disposable sample.

Offline and off-policy learning are related but not identical. Offline learning uses a fixed dataset. Off-policy learning trains the current policy using trajectories generated by another policy, τ ~ πold, while optimizing πnew. This matters when rollout generation is slow and a useful trajectory is several policy versions old.

On-policy distillation

On-policy distillation offers a useful middle ground. SFT provides dense supervision but is off-policy; RL is on-policy but often has only a sparse final reward. With on-policy distillation, the student visits its own states and mistakes while a stronger teacher provides a denser signal on those same trajectories.

SFT                    RL
teacher trajectory      student trajectory
→ student imitates      → final reward
dense, off-policy       on-policy, sparse

ON-POLICY DISTILLATION
student trajectory → teacher evaluates student states
                   → dense, on-policy supervision

This is especially interesting for long-horizon agents because the teacher can provide information about where a student trajectory went wrong without requiring a reward for every token or tool call.

Curriculum by horizon length

Do not begin with twelve hours. Start with five minutes, then fifteen minutes, one hour, three hours, six hours, and finally twelve hours—or increase the action horizon from 10 to 50, 200, 500, and 1,000 or more steps. The model first learns the local rules of the world; then we increase the time for which it must remain coherent.

curriculum = [20, 50, 150, 500, 1500]

for max_steps in curriculum:
    env.set_max_steps(max_steps)
    while not ready_to_advance(policy, env):
        trajectories = collect_rollouts(policy, env)
        policy = rl_update(policy, trajectories)

An adaptive curriculum can promote the model when evaluation success passes a threshold, such as if eval_success_rate > 0.80: horizon *= 2. Short horizons teach mechanics, medium horizons teach planning, long horizons teach persistence, and very long horizons expose delayed consequences.

Hierarchical credit assignment

At very long horizons, one reward attached to the entire episode is often not enough to explain what happened. A twelve-hour task naturally contains a hierarchy: verify coverage, collect evidence, investigate inconsistencies, communicate with the claimant, and produce a final decision. Instead of treating the trajectory only as (a1, a2, …, a1000), segment it into meaningful subtrajectories τ = (τ1, τ2, …, τk).

This lets the trainer ask which subtask caused the failure before asking which individual token caused it. A coding trajectory might be segmented into understanding the issue, locating the bug, designing a patch, implementing it, running tests, repairing failures, and submitting. A hierarchical return can combine final and subtask outcomes: R(τ) = Rfinal + Σi λiRsubtask,i.

Intermediate rewards should correspond to meaningful, independently verifiable state changes rather than arbitrary signals such as “used the right tool.” Otherwise, hierarchy creates more surfaces for reward hacking instead of making failure interpretable.

A practical training stack

Putting the pieces together, a practical long-horizon training setup might look like:

environment platform → parallel trajectories → trajectory store
→ SFT + offline learning → on-policy RL / distillation
→ curriculum increases horizon → new trajectories → repeat

The environment platform supplies states, sandboxes, tools, and verifiers. A training system supplies SFT, RL, distillation, optimizer steps, and checkpointing. Prime Intellect is most relevant when the environment itself is central to the experiment, while Tinker represents a programmable training layer where the researcher provides the data, environment, loss, and loop.

The central insight is that training on long-horizon environments should be a continual improvement loop: collect → filter → imitate → explore → evaluate → increase horizon → repeat. SFT teaches the shape of successful work. RL teaches recovery when the agent leaves that distribution. Offline methods make expensive trajectories reusable. Curriculum makes exploration tractable. Hierarchical credit assignment makes failure interpretable.

For long-horizon agents, the scarce resource may eventually be less the gradient update itself and more the high-quality trajectory through a consequential world.

Evaluating Long-Horizon Agents

Training reward tells us whether a policy is improving. Evaluation asks a harder question: does the trained agent actually behave better across complete long-horizon trajectories it has not seen before?

For a twelve-hour agent, final accuracy alone is not enough. Two agents can reach the same outcome while one wastes compute, repeats work, violates constraints, or succeeds only after recovering from several serious mistakes.

Task success

Start with the clearest signal: Success ∈ {0, 1}. Did the agent actually complete the task? For coding, this might mean hidden tests pass. For an insurance workflow, the final decision and required state transitions must be correct. Wherever possible, this evaluator should be objective and externally verifiable.

Trajectory quality

Then inspect how the agent got there. A trajectory evaluator can look for unnecessary loops, repeated actions, poor information gathering, premature commitments, bad intermediate decisions, or actions that happened to work despite weak reasoning. The object being evaluated is therefore the complete trajectory, τ = (s0, a0, …, sT), not merely the final answer.

Efficiency and recovery

Long-horizon environments should record the cost of success: tool calls, tokens, world time, compute, retries, and unnecessary actions. Recovery is especially important. If the environment changes unexpectedly or an early decision fails, can the agent recognize the failure, update its plan, and continue?

A useful agent is not one that never fails. It is one that can fail without losing the entire trajectory.

Constraint adherence and delayed consequences

Some failures should invalidate an otherwise successful trajectory. An agent might solve a coding task while exposing credentials, approve the correct claim while violating procedure, or finish quickly by taking an unauthorized shortcut.

Some consequences appear only later. Evaluation should be able to advance the environment after the apparent completion point and check whether earlier actions created delayed failures: actiont → consequencet+k. A policy that leaves the world in a dangerous state should not receive full credit merely because the immediate task appeared complete.

Evaluating after training with Prime Intellect

Prime Intellect provides a useful implementation of this loop. Its Verifiers framework defines tasksets, tools, harnesses, runtimes, and scoring rubrics, so the same environment can be used during training and evaluation.

After training a policy, it can be run through held-out environments in parallel. In this setup, the platform handles inference, sandboxes, rollout execution, and result collection, while the environment evaluator or rubric determines performance.

This makes the train → evaluate → inspect → retrain loop part of the same stack. For long-horizon agents, the final question should not simply be, “Did it finish?”

What Should We Build Next?

The most interesting long-horizon environments are not short tasks artificially stretched to make them harder. They are domains where the real work already unfolds over hours, days, weeks, or months. These environments naturally contain waiting, external events, changing state, multiple actors, delayed consequences, and decisions that cannot always be reversed.

Insurance

Insurance is one of the clearest places to start. A claim is a persistent process: an adjuster collects evidence, reads policies, contacts the claimant, waits for documents, handles inconsistencies, updates reserves, checks coverage, and eventually decides whether and how much to pay.

An insurance agent could remain attached to a claim throughout its lifecycle. It might work for twenty minutes, wait six hours for a document, wake when the document arrives, update its understanding, request more evidence, and eventually make a consequential decision. That is a genuine long-horizon environment.

Guidewire is already moving toward agentic infrastructure across policy, claims, and billing systems. The deeper research opportunity is not simply making claims faster; it is evaluating whether an agent can maintain a correct belief for several days, handle contradictory evidence, respect authorization constraints, communicate appropriately, recover from mistakes, and understand the financial consequences of its decisions.

Legal

Legal work is naturally sequential. A contract can move through drafting, review, negotiation, counterparty comments, revision, approval, execution, and later interpretation. A litigation matter can evolve over months as new evidence appears, opposing counsel responds, deadlines change, and earlier decisions affect later options.

Harvey’s Legal Agent Benchmark is a useful example of vertical evaluation: instead of asking isolated legal questions, it gives an agent a client matter containing multiple documents and asks it to produce actual legal work product. The same pattern could extend to insurance, finance, compliance, and healthcare operations.

Manufacturing

Manufacturing is an almost perfect long-horizon environment because the world never stops. Machines produce telemetry, equipment degrades, parts arrive late, quality issues appear, workers change shifts, and production schedules move. Maintenance decisions made in the morning may affect throughput twelve hours later.

Instead of asking an agent to diagnose one machine failure, the environment could ask it to operate a production line for twelve simulated hours while maximizing throughput, maintaining quality, responding to failures, and staying inside safety constraints. NVIDIA’s factory-operations work points toward this kind of continuously observing and orchestrating agent.

Farming

A farm pushes the horizon even further. Weather, soil, crop health, machinery, labor, irrigation, disease, input prices, and biological processes evolve continuously, while some decisions have consequences that appear days or months later.

A genuinely ambitious benchmark would not ask, “Identify weeds in this image?” It would ask, “Manage this farm for an entire simulated growing season.” The agent would coordinate irrigation, respond to disease pressure, reschedule work around weather, operate machinery, and learn from outcomes across the season. Platforms such as John Deere Operations Center show how machine, field, and environmental data can become the state and action interfaces for such an environment.

Scientific research

Scientific research forms a long loop: an agent proposes a hypothesis, modifies code, launches an experiment, waits for results, analyzes failures, reads related work, changes direction, and runs another experiment. The objective itself may change as evidence accumulates.

This is an area where final answers are especially incomplete. Evaluation needs to inspect how an agent frames problems, executes experiments, responds to feedback, reuses previous experience, and decides when to abandon an unproductive direction. A research environment should measure sustained exploration and the quality of the investigation, not only whether the final report sounds plausible.

Chip design

Chip design is another strong example of long-horizon engineering becoming agentic. An agent may generate RTL, run simulations, inspect failures, change the design, rerun verification, and iterate toward design closure while balancing power, performance, and area. Those loops already take humans days or weeks.

Cadence and Synopsys both describe increasingly autonomous systems for chip design and verification. A useful benchmark would measure not only whether the final design works, but tool cost, progress over time, recovery from failed simulations, and performance across different stages of the hardware flow.

Finance, cybersecurity, and operations

Many other domains have the same structure. A financial operations agent might manage reconciliations, investigate exceptions, wait for counterparties, monitor settlement, and make decisions involving real economic constraints. A cybersecurity agent might investigate an incident for hours, gather evidence from several systems, contain compromised infrastructure, monitor whether the attacker returns, and update its response as telemetry changes. A supply-chain agent could monitor inventory, suppliers, shipping delays, warehouses, and demand continuously.

The common feature is not the industry. It is the temporal structure of the work: persistent state, asynchronous events, scarce resources, multiple actors, uncertainty, and delayed consequences.

Match the environment horizon to the work

Instead of building another benchmark where an agent receives a prompt and finishes ten minutes later, we can build persistent environments that represent actual economic and scientific processes. Then we can ask increasingly ambitious questions:

  • Can an agent manage a claim for three days?
  • Can it operate a factory for twenty-four hours?
  • Can it conduct fifty experiments without losing the research objective?
  • Can it manage a farm across a growing season?
  • Can it drive a chip from specification toward verification closure?

The goal is not simply to make benchmarks longer. It is to make the environment horizon match the natural horizon of the work. That is when long-horizon agents become more than better chatbots: they become systems that can remain responsible for an evolving piece of the world.

Conclusion

The shift from short agent tasks to long-horizon work changes what matters. A capable model is no longer enough. An agent working for hours or days needs a world that persists around it: state that survives restarts, memory that keeps only what matters, events that arrive asynchronously, tools that change the world, checkpoints that enable recovery, and rewards that still mean what we intend after thousands of actions.

This is why long-horizon agents increasingly look less like chat systems and more like distributed systems. The model provides reasoning and action selection, but the surrounding environment provides continuity, time, access control, synchronization, observability, and consequences.

Training must change as well. Successful trajectories can become supervised fine-tuning data, expensive rollouts can be reused offline, reinforcement learning can improve behavior beyond demonstrations, and curriculum learning can gradually extend the horizon from minutes to hours. Evaluation must also move beyond final accuracy. We should measure whether the agent completed the task, how efficiently it acted, whether it recovered from failure, respected constraints, and left the world in a good state afterward.

The most valuable environments will come from work that is already long-running: insurance claims, legal matters, manufacturing, farming, scientific research, chip design, cybersecurity, and operations.

The goal is not to make benchmarks longer for the sake of difficulty. It is to build persistent worlds whose time horizon matches the real work, then train agents that can remain useful, coherent, and accountable inside them. That is the architecture required for agents that truly endure.
